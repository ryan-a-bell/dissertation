\section{Methodological Framing and Traceability to Research Objectives}
\label{sec:ch3_framing}

Chapter~\ref{ch:introduction} defined a set of Research Objectives in Section~\ref{sec:research_objectives} that constitute the intentional, executable actions required to answer the research questions in Section~\ref{sec:research_questions}. This research was executed through an empirical pipeline that is organized explicitly around those Research Objectives to preserve traceability between declared intent and implemented methodology.

The pipeline describes the chronological sequencing of work. However, chronological sequencing alone does not make explicit how each step contributes to the production of qualification-relevant evidence. Because this dissertation frames model evaluation as a qualification problem that requires modality-aware, robustness-aware, and cost-aware evidence, Chapter~\ref{ch:materials_methods} is structured around the objectives themselves. Each objective defines the work performed, the artifacts produced, and the evidence generated. 

Objective~7 is not addressed in this chapter, as it concerns synthesis and integration of findings and is therefore fulfilled in Chapter~5. All other objectives are executed through the pipeline described below, with the execution environment and reproducibility controls presented first as are cross-cutting across all objectives. Subsequent sections correspond directly to the Research Objectives listed in Section~\ref{sec:research_objectives}. 

The methodological framework connects the research questions posed in Chapter~\ref{ch:introduction} to inference execution, scoring, and analysis. It transforms the base SysEngBench dataset~\cite{bell_RabellSysEngBenchDatasets_2024} through deterministic dataset derivation procedures, evaluates \acp{llm} across both \ac{mcq} and \ac{osq} formats under standardized inference controls, applies rubric-based LLM-as-a-Judge scoring for open responses, and performs statistical analyses tailored to each objective.

Figure~\ref{fig:modality_eval_pipeline} illustrates the high-level data flow through this pipeline. Each stage produces well-defined artifacts, including datasets, model responses, scoring outputs, and statistical results that serve as inputs to subsequent stages. These artifacts are retained and versioned to preserve traceability from final claims back to originating data and configuration settings. The pipeline functions not merely as an execution sequence, but as a traceable thread aligned directly to the declared Research Objectives.

\subsection{Tooling and Evaluation Orchestration}
\label{subsec:ch3_tooling_orchestration}

All code, notebooks, task configurations, and analysis scripts were version-controlled using Git and hosted in the dissertation repository on GitHub at \texttt{ryan-a-bell/dissertation}. Python package dependencies are captured in \texttt{requirements.txt}, enabling reconstruction of the software environment used to produce the reported artifacts.

The harness provides:
\begin{itemize}
    \item Consistent prompt formatting and task execution across models,
    \item Automatic metric computation for MCQ tasks (e.g., accuracy ),
    \item Structured outputs (JSON aggregate results and JSONL per-item sample logs), and
    \item Support for custom tasks and configurations via YAML.
\end{itemize}

Scripts were used for dataset processing, rubric generation, and post-hoc analysis. All tooling was integrated within a repository-managed workflow to ensure that dataset versions, prompts, and evaluation configurations remain synchronized with the reported results.

\subsection{Compute Environment and Inference Backends}
\label{subsec:ch3_compute_backends}

Model inference required GPU resources due to the number of models evaluated and the size of certain models, including models exceeding 272B parameters. \ac{gpu} compute was provisioned through RunPod, a cloud \ac{gpuaas} platform offering on-demand access to multiple NVIDIA GPU classes (e.g., A40, A100, H200). This enabled rapid iteration on evaluation configurations, consistent environment setup, and the ability to evaluate large models that were impractical to host locally although the framework is \ac{gpuaas} agnostic.

GPU selection was driven primarily by each model's memory requirements. Larger models were placed on the highest-capacity \acp{gpu} available to ensure sufficient \ac{vram} headroom for inference overhead and optimized execution. Smaller models were scheduled onto appropriately sized instances to maintain efficient resource utilization.

Each RunPod instance was configured with:
\begin{itemize}
    \item PyTorch container template (CUDA 12.1, PyTorch 2.1+),
    \item Exposed port 11434 for Ollama API access,
    \item Persistent volume storage for model weights and run artifacts,
    \item SSH access for command-line operations, and
    \item Optional JupyterLab interface for interactive debugging.
\end{itemize}

For local open-weight inference, Ollama served as the inferencing service, providing an OpenAI-compatible API endpoint at \texttt{http://localhost:11434/v1/chat/completions}. Ollama handled model loading, memory management, and efficient inference. Models were pulled systematically from the Ollama registry using \texttt{ollama pull <model\_name>} and verified with \texttt{ollama list}.

Primary development occurred on a local workstation running Windows 11 with Python 3.12.4. Jupyter notebooks were used for exploratory analysis and prototyping, while production evaluation scripts were executed on RunPod GPU instances.

To reduce sources of uncontrolled variance, inference was performed with deterministic decoding settings where supported (see Section~\ref{subsec:ch3_run_controls}). In addition, model and infrastructure heterogeneity (local inference vs.\ hosted APIs) was treated as an explicit experimental reality; the workflow retains sufficient run metadata to reconstruct which provider, model identifier, and configuration produced each output.

The Figure \ref{fig:icd-scalable-workers} illustrates a scalable GPU-based inference and computation workflow built on top of RunPod, although the framework is GPU provider agnostic. At the top, a user interacts through a Jupyter Notebook running in a local execution environment. This environment spawns multiple subprocesses, each acting as a runner, which communicate with remote GPU pods. These subprocesses form the client-side layer that initiates tasks, sends workloads to the cloud, and receives results. Their interaction with the notebook is bidirectional, enabling parallel job submission and coordination from a single interactive workspace.

Beneath the local layer is the RunPod cloud infrastructure, which hosts an orchestrator and a pool of GPU-backed pods. The orchestrator manages communication channels, routing tasks from local subprocesses to the appropriate pods via dedicated DirectChannel links. Each pod contains a GPU Runner responsible for executing the assigned workload. The architecture supports multiple pods (1 through N), enabling horizontal scaling as demand grows.

\subsection{Dataset Versioning and Artifact Management}
\label{subsec:ch3_artifacts}

SysEngBench and all derived datasets were managed as versioned artifacts to support traceability between dataset construction and evaluation outcomes. The base dataset was retrieved from Hugging Face (\texttt{rabell/SysEngBench}) via API access and is publicly hosted for reproducibility~\cite{bell_RabellSysEngBenchDatasets_2024}. Derived datasets (OSQ-converted sets and MCQ positional variants) were constructed deterministically from the base dataset and stored with explicit identifiers (e.g., \texttt{-A}, \texttt{-B}, \texttt{-C}, \texttt{-D}, \texttt{-OSQ}); these derivative datasets are also publicly hosted for reproducibility \cite{bell_RabellSysEngBenchADatasets_2025, bell_RabellSysEngBenchBDatasets_2025, bell_RabellSysEngBenchCDatasets_2025, bell_RabellSysEngBenchDDatasets_2025, bell_RabellSysEngBenchOSQ_2026}


Versioning discipline is essential for traceability: even minor modifications to prompt templates, item filtering criteria, or answer-option rotation can affect measured performance. To support repeatability and retrospective auditing, artifacts were retained at each stage of the pipeline:
\begin{itemize}
    \item Dataset artifacts: dataset versions, item identifiers, conversion outputs, and rotation maps.
    \item Inference artifacts: prompts, raw model responses, and response metadata such as model id, backend/provider, inference parameters.
    \item Scoring artifacts: judge prompts, judge outputs, structured rubric scores, and stability-check outputs where applicable.
    \item Analysis artifacts: aggregated result tables and statistical test outputs used to generate reported figures and claims.
\end{itemize}

Sensitive credentials (e.g., Hugging Face tokens or OpenRouter API keys) were stored in a local \texttt{.env} file excluded from version control; a template (\texttt{.env.template}) is provided for reproducible setup.

\subsection{Run Standardization: Determinism, Retries, and Token Accounting}
\label{subsec:ch3_run_controls}

Across all inference runs, settings were standardized to reduce avoidable variance and improve comparability:

\begin{itemize}
    \item Deterministic runs: temperature set to \texttt{0.0}, with consistent maximum token limits and stop sequences when applicable.
    \item Prompt standardization: task templates and instruction framing were held fixed within each evaluation condition.
    \item Controlled retry policy: transient API failures or invalid outputs were retried under a documented policy; retries and failures were retained as artifacts to preserve auditability.
\end{itemize}

Two external services were used to support dataset access and API-based inference:
\begin{itemize}
    \item Hugging Face was used to retrieve and version benchmark artifacts (datasets), enabling stable dataset identifiers and reproducible access patterns.
    \item OpenRouter was used to access proprietary foundation models through a single API endpoint. This simplified evaluation orchestration across providers while preserving consistent logging and configuration capture.
\end{itemize}

OpenRouter exposes a common parameter interface (e.g., temperature) and routes requests to provider endpoints. Parameter defaults and supported options vary across providers, so model-specific capability constraints were handled explicitly in the run configuration rather than assumed.\footnote{\url{https://openrouter.ai/docs/api/reference/parameters}}

Token usage and response length are to be measured to support Objective~6. For each inference call, input and output token counts were recorded. Token counts were computed using a consistent tokenizer-based accounting policy. Token accounting distinguishes between OSQ model responses and OSQ judge scoring as separate passes. Token counts are recorded as the primary, price-agnostic resource metric and intentionally excludes monetary pricing due to volatile provider schedules.

\section{Objective 1: Benchmark Curation and Derivative Construction}
\label{sec:ch3_obj1}

\subsection{Baseline Benchmark Acquisition and Characteristics}
\label{subsec:ch3_obj1_baseline}

SysEngBench is a \ac{mcq} benchmark for systems engineering, aligned to the INCOSE Systems Engineering Handbook \cite{bell_IntroducingSysEngBenchNovel_2024}. The dataset was downloaded from Hugging Face (\texttt{rabell/SysEngBench}) via API access \cite{bell_RabellSysEngBenchDatasets_2024}. The test split contains 1,144 questions spanning six major \ac{incose} knowledge areas and 20 sub-categories.

Each question record includes the following fields:
\begin{itemize}
    \item \texttt{question\_id}: Unique numeric identifier.
    \item \texttt{question}: Question stem text.
    \item \texttt{choices}: Four answer choices (A--D).
    \item \texttt{answer}: Correct answer (A--D).
    \item \texttt{justification}: A short rationale supporting the correct answer.
    \item \texttt{category}: INCOSE knowledge area category label.
    \item \texttt{subcategory}: INCOSE subcategory label.
\end{itemize}

These fields provide the minimum metadata required to support both robustness analysis in the MCQ setting and conversion to OSQ variants with canonical expected answers and rubrics (Objective 2).

An extensive analysis of the benchmark was conducted in \cite{Bell2025SysEngBench} that includes sub-categories with distributions visualized using bar charts, pie charts, and stacked visualizations to express the coverage of the benchmark across the systems engineering domain.


\subsection{Construction of MCQ Robustness Variants}
\label{subsec:ch3_obj1_mcq_variants}

To detect position bias in model responses to \acp{mcq}, as demonstrated in \cite{zhengLargeLanguageModels2024}, four variants of the SysEngBench dataset were generated with correct answers systematically rotated to positions A, B, C, and D. This approach enables statistical testing for underlying preference for answer positions.

The rotation procedure preserves question content and choice semantics while permuting answer-option ordering. For each base item, a rotation map is computed such that each of the four variants places the correct answer in a different position while maintaining a consistent permutation structure over the four options. This produces four aligned datasets:

\begin{itemize}
    \item \textbf{SysEngBench-A\footnote{\url{https://huggingface.co/datasets/rabell/SysEngBench-A}}}: Correct answer at position A (label=0)
    \item \textbf{SysEngBench-B\footnote{\url{https://huggingface.co/datasets/rabell/SysEngBench-B}}}: Correct answer at position B (label=1)
    \item \textbf{SysEngBench-C\footnote{\url{https://huggingface.co/datasets/rabell/SysEngBench-C}}}: Correct answer at position C (label=2)
    \item \textbf{SysEngBench-D\footnote{\url{https://huggingface.co/datasets/rabell/SysEngBench-D}}}: Correct answer at position D (label=3)
\end{itemize}

Because each variant contains the same questions under systematic reordering, differences in accuracy across variants can be attributed to positional sensitivity rather than content differences.

\subsection{MCQ to OSQ Conversion Process}
\label{subsec:ch3_obj1_alignment}

The conversion process from \ac{mcq} to \ac{osq} consists of two sequential stages: (1) suitability classification, and (2) conversion with rubric generation. Figure \ref{fig:mcq-to-osq} illustrates the complete pipeline.


\begin{figure}[htbp]
    \centering

    \subfloat[MCQ Check for Convert-ability]{%
        \includegraphics[width=0.48\textwidth]{figs/ch3/3.3/filter-mcqs.png}
    }\hfill
    \subfloat[Conversion of MCQ to OSQ]{%
        \includegraphics[width=0.48\textwidth]{figs/ch3/3.3/convert-mcq-to-osq.png}
    }

    \caption{Multiple Choice Question to Open Style Question Workflow}
    \label{fig:mcq-to-osq}
\end{figure}

Stage 1 classifies each MCQ for OSQ suitability across five key elements. Questions scoring $\geq 7/10$ proceed to Stage 2, where conversion generates a OSQ prompt, expected answer, grading rubric, and Bloom's taxonomy classification. 

\paragraph{Stage 1: Suitability Classification}

The suitability classifier filters out items where the OSQ form would be ambiguous, underspecified, or would fail to preserve the original measurement intent. Suitable items are then converted into OSQs and paired with canonical expected answers and structured rubrics.
%% COMBINE THESE TWO PARAGRAPHS
Not all multiple-choice questions are suitable for conversion to open-ended format. Questions requiring visual diagrams, those with highly ambiguous correct answers, or those where the distractor options provide essential context may not translate well.

Each of the \acp{mcq} was evaluated by ChatGPT-5 via OpenRouter with a temperature of 0 across five key elements, including:

\begin{enumerate}
    \item \textbf{Assessability}: Can the answer be evaluated objectively in open-ended format?
    \item \textbf{Canonical Answer Clarity}: Is there a well-defined expected answer?
    \item \textbf{Ambiguity}: Is the question clear without the MCQ structure?
    \item \textbf{Scope Appropriateness}: Is the expected answer reasonable in length for short-answer format?
    \item \textbf{Intent Preservation}: Can the original knowledge construct be maintained without MCQ options?
\end{enumerate}

The \ac{llm} returned a structured JSON response containing:
\begin{lstlisting}[language=json,
    basicstyle=\ttfamily\footnotesize,
    caption={Structure of the LLM evaluation output},
    label={lst:llm-json}
]

{
  "suitability_score": <1-10>,
  "justification": "<reasoning>",
  "dimension_scores": {
    "assessability": <1-10>,
    "canonical_answer": <1-10>,
    "ambiguity": <1-10>,
    "scope": <1-10>,
    "intent_preservation": <1-10>
  }
}
\end{lstlisting}

The complete classification prompt is provided in Appendix~\ref{appendix-a}.

\paragraph{Stage 2: Conversion with Rubric Generation}

For each suitable \ac{mcq}, ChatGPT-5 was used to perform the conversion. The conversion process:

\begin{itemize}
    \item Removed MCQ-specific artifacts (e.g., ``which of the following'', explicit A/B/C/D options)
    \item Maintained the original intent (e.g., definition recall remains recall, not application)
    \item Preserved any numerical calculations or technical specifications
    \item Generated a canonical expected answer based on the original correct choice
    \item Created a grading rubric with three levels:
    \begin{itemize}
        \item \textbf{Full credit}: Criteria for complete correct answer
        \item \textbf{Partial credit}: Criteria for partially correct answer
        \item \textbf{No credit}: Conditions warranting no credit
    \end{itemize}
    \item Assigned Bloom's taxonomy level (Remember, Understand, Apply, Analyze, Evaluate, Create)
\end{itemize}

The conversion prompt explicitly instructed the LLM to ``keep the construct and difficulty comparable'' for \acp{osq}, maintaining parity with the original \ac{mcq} construct.

The response for the conversion prompt is a structured JSON:

\begin{lstlisting}[language=json,
    basicstyle=\ttfamily\footnotesize,
    caption={Structure of the OSQ generation prompt},
    label={lst:osq-json}
]
{
  "osq_prompt": "<open-ended question>",
  "expected_answer": "<canonical answer>",
  "rubric": {
    "full_credit": "<criteria>",
    "partial_credit": "<criteria>",
    "no_credit": "<criteria>"
  },
  "blooms_level": "<taxonomy level>",
  "blooms_justification": "<reasoning>"
}
\end{lstlisting}

The first was chosen for its comprehensive assessment of single responses approach and rubric grading, and tailored to the \ac{se} domain in Figure \ref{lst:osq-grading-prompt}. The full prompt may be found Appendix \ref{app:llm-as-a-judge-prompt}

\subsection{Inter-Judge Reliability and Stability Analysis}
\label{subsec:ch3_obj4_reliability}

To validate OSQ scoring as a measurement instrument, both inter-judge agreement and score stability were evaluated. For responses scored by multiple judges, agreement was quantified using Spearman's rank correlation between judges' total scores. High correlation indicates that judges produce consistent relative orderings of responses and models. Judge scoring was conducted under identical conditions and is idempotent with a temperature of 0 to assess run-to-run stability. 


\paragraph{Predefined Reliability Classification Criteria}
To preserve separation between results in Chapter \ref{ch:results} and discussion and interpretation in Chapter \ref{ch:discussion}, reliability levels are classified using predefined thresholds applied systematically to observed results.

Reliability is evaluated using the following procedure:

\begin{enumerate}[nosep]
    \item Score Distribution Diagnostics: For each model--judge combination, score distributions are examined to assess whether the scoring instrument produces structured and differentiable outputs. The following properties are recorded:
    \begin{itemize}[nosep]
        \item \textit{Modality:} uni-modal versus multi-modal distributions
        \item \textit{Spread:} dispersion measured via standard deviation and interquartile range
        \item \textit{Compression effects:} floor or ceiling clustering
        \item \textit{Skewness:} asymmetric score allocation patterns
    \end{itemize}
    
Highly compressed or extreme clustering distributions indicate limited discriminative resolution, while multi-modal or irregular shapes may suggest heterogeneous rubric application across response types. These properties characterize the measurement behavior of the scoring instrument but do not in themselves determine adequacy.

    \item Inter-judge agreement: Correlation quantifies consistency in relative ordering rather than absolute calibration. These thresholds are used to categorize scoring stability across judges under identical rubric conditions.

    Let $\rho$ denote Spearman's rank correlation:
    \begin{itemize}[nosep]
        \item $\rho \geq 0.80$ — High agreement
        \item $0.50 \leq \rho < 0.80$ — Moderate agreement
        \item $\rho < 0.50$ — Low agreement
    \end{itemize}
    

\end{enumerate}

These criteria determine whether the rubric-based judge framework satisfies minimum reliability requirements as a measurement instrument. Substantive implications for model capability and modality trade-offs are reserved for Chapter~5.

\section{Objective 5: Robustness and Cross-Modality Evidence Uncertainty Quantification}
\label{sec:ch3_obj5}

Objective 5 strengthens the interpretability of benchmark outcomes by (i) testing the robustness of MCQ results to answer-position artifacts using position-rotated variants and (ii) establishing a cross-modality comparison framework between MCQ and OSQ formats on one-to-one matched questions. Together, these analyses support defensible model comparisons  by clarifying when different evaluation modalities provide convergent versus complementary evidence.

% ---------------------------------------------------------
\subsection{MCQ Robustness via Answer-Position Rotations}
\label{subsec:ch3_obj5_mcq_robustness}

With construction of the datasets was discussed in Section \ref{subsec:ch3_obj1_mcq_variants}, this section focuses on the quantification of the results for MCQ robustness.


\paragraph{Position bias as a robustness failure mode.}
Position bias refers to systematic preference for particular answer positions (A, B, C, D) independent of question content. If present, such bias can inflate or deflate apparent model accuracy depending on the distribution of correct answers in the benchmark, confounding cross-model comparisons.

To test robustness to this failure mode, each MCQ item is evaluated under four position-rotated variants in which the correct option appears once in each position (A, B, C, D) while preserving the underlying question and distractor content. Let $\text{Acc}_p$ denote accuracy when the correct answer appears in position $p \in \{A,B,C,D\}$:
\begin{align}
\text{Acc}_A &= \frac{\#\text{ correct on variant A}}{N} \\
\text{Acc}_B &= \frac{\#\text{ correct on variant B}}{N} \\
\text{Acc}_C &= \frac{\#\text{ correct on variant C}}{N} \\
\text{Acc}_D &= \frac{\#\text{ correct on variant D}}{N},
\end{align}
where $N$ is the number of MCQ items evaluated per variant. Under the null hypothesis of no position bias, $\text{Acc}_A=\text{Acc}_B=\text{Acc}_C=\text{Acc}_D$.

Robustness is supported when (i) accuracy does not differ meaningfully across positions with global invariance, (ii) within-item correctness is stable across rotations with item-level invariance, and (iii) any detected differences are negligible in magnitude as quantified by standardized effect sizes.

\paragraph{Statistical tests and effect sizes.}
Two complementary nonparametric tests are applied for each model to distinguish between global position dependence and within-item sensitivity:

\begin{itemize}[leftmargin=*, itemsep=0.5em]
\item \textbf{Chi-square test of independence} ($\chi^2$) with \textbf{Cram\'{e}r's $V$}:
  \begin{itemize}[leftmargin=*, itemsep=0.25em]
    \item \emph{Design:} correctness ($\in\{\text{correct},\text{incorrect}\}$) cross-tabulated by answer position ($\in\{A,B,C,D\}$).
    \item \emph{Test:} whether aggregate correctness is independent of answer position (global dependence).
    \item \emph{Effect size:} Cram\'{e}r's $V$ quantifies the magnitude of association, reducing reliance on p-values alone.
  \end{itemize}

\item \textbf{Friedman test} (repeated measures) with \textbf{Kendall's $W$}:
  \begin{itemize}[leftmargin=*, itemsep=0.25em]
    \item \emph{Design:} repeated measures across the same underlying items evaluated under position-rotated variants.
    \item \emph{Test:} whether per-item correctness differs systematically across positions (within-item sensitivity).
    \item \emph{Effect size:} Kendall's $W$ quantifies the consistency and strength of position effects across items.
  \end{itemize}
\end{itemize}


\subsubsection*{Predefined Robustness Classification Criteria}
\label{subsubsec:ch3_obj5_mcq_robustness_criteria}

To preserve separation between results in Chapter \ref{ch:results} and discussion and interpretation in Chapter \ref{ch:discussion}, this section defines the criteria by which answer-position robustness will be classified. These criteria are applied systematically to the observed results.


% We employed non-parametric inferential statistical tests to evaluate both statistical significance and effect magnitude. Specifically, the Chi-Square test of independence ($\chi^2$) was used to assess categorical associations, with Cram\'{e}r's~$V$ reported as the corresponding effect size. 
% For repeated-measures analyses, the Friedman test ($Q$) was applied, and Kendall's~$W$ was reported to quantify effect magnitude.


For each model, robustness to answer-position artifacts is evaluated using joint evidence from two complementary statistical perspectives and their combination: 
(i) global (aggregate-level) position dependence,  
(ii) within-item (repeated-measures) position sensitivity, and 
(iii) classification of the evidence

\begin{enumerate}[nosep]

    \item \textbf{Global position dependence (aggregate-level robustness).}

    We first assess whether overall correctness rates differ depending on the answer position in which the correct option appears. 
    For each model, responses are summarized in a $2 \times 4$ contingency table that cross-tabulates:

    \begin{itemize}[nosep]
        \item \textbf{Correctness} $\in \{\text{correct}, \text{incorrect}\}$, and
        \item \textbf{Answer position} $\in \{A, B, C, D\}$.
    \end{itemize}

    Concretely, the table contains counts of correct and incorrect responses when the correct answer is placed in each position (A, B, C, or D). 
    If robustness holds at the aggregate level, the proportion of correct responses should be approximately equal across all four positions.
    We apply a chi-square test of independence to evaluate whether correctness is statistically independent of answer position. 
    Because large sample sizes can render trivial differences statistically significant, we report Cram\'{e}r's $V$ as a standardized effect size to quantify the practical magnitude of any detected association. 
    This test captures \emph{aggregate} distortions in measured accuracy due to answer placement.

    \item \textbf{Within-item position sensitivity (repeated-measures robustness).}

    Aggregate stability does not guarantee item-level stability. 
    Even if overall accuracy appears similar across positions, individual questions may flip between correct and incorrect when the correct option is rotated.
    Because each of the four rotated variants contains the same underlying items and only the option order differs, correctness across positions forms a repeated-measures design at the item level. 
    Each question is effectively evaluated four times per model, once with the correct answer in each position.
    To assess whether correctness for the same items changes systematically across rotated positions, we apply the Friedman test, a nonparametric test for repeated measures. 
    We report Kendall's $W$ as the corresponding repeated-measures effect size, which quantifies the strength and consistency of within-item position effects.


    \item \textbf{Classification.}
    Models are classified with the decision tree found in Figure \ref{fig:mcq-robustness-decision-tree} and all permutations summarized in Table~\ref{tab:position_bias_rubric}. Effect sizes ($V$, $W$) are treated as primary indicators of practical relevance, while p-values are used to determine whether observed effects are distinguishable from noise under the available sample size.

\end{enumerate}

The procedural outputs of this robustness analysis (test statistics, p-values, and effect sizes) are reported in Chapter~\ref{ch:results}. Substantive implications for benchmark validity, model comparison, and qualification evidence are discussed in Chapter~\ref{ch:discussion}.

\subsection{Cross-Modality Comparison Framework}
\label{subsec:ch3_obj5_modality_comparison}

This subsection evaluates whether MCQ and OSQ formats yield convergent assessments of model capability on matched questions, or whether they capture systematically different aspects of performance. If MCQ and OSQ diverge, scores from the two formats should not be treated as interchangeable evidence.

To preserve separation between results in Chapter \ref{ch:results} and discussion and interpretation in Chapter \ref{ch:discussion}, this subsection defines criteria used to classify whether MCQ and OSQ provide convergent evidence on the matched question subset. The criteria below are applied systematically to the observed results.

\begin{enumerate}[nosep]
    \item \textbf{Visual consistency diagnostic.}
    A scatter plot is constructed with MCQ accuracy on the $x$-axis and normalized mean OSQ score on the $y$-axis, one point per model. The diagonal reference line $y=x$ is used as a qualitative guide for agreement. Systematic displacement above/below the diagonal is recorded as a diagnostic of directional separation between formats.

    \item \textbf{Association and ranking agreement.}
    Pearson's correlation ($r$) is computed to quantify linear association and Spearman's rank correlation ($\rho_s$) to quantify agreement in model ordering.

    Association levels are classified as:
    \begin{itemize}[nosep]
        \item \textbf{High association:} $r \ge 0.80$ \emph{and} $\rho_s \ge 0.80$, MCQ and OSQ largely agree on model ordering; they measure closely related constructs.
        \item \textbf{Moderate association:} $0.50 \le r < 0.80$ \emph{or} $0.50 \le \rho_s < 0.80$, Formats are moderately aligned but capture partially distinct capabilities.
        \item \textbf{Low association:} $r < 0.50$ \emph{or} $\rho_s < 0.50$, Formats diverge; MCQ and OSQ should be treated as measuring different aspects of performance.
    \end{itemize}

    We compute Pearson's correlation to assess linear association between MCQ accuracy and mean OSQ score across models, and Spearman's rank correlation to assess whether the two formats induce similar model orderings. High correlation would suggest convergent evidence; lower correlation would suggest that formats capture partially distinct capabilities.

    \item \textbf{Paired difference test.}
    For each model $i$, we compute the difference between MCQ accuracy and normalized OSQ mean score on the matched subset,
\[
\Delta_i = \text{Acc}_{\text{MCQ},i} - \bar{S}'_{\text{OSQ},i}.
\]
We apply the Wilcoxon signed-rank test to $\{\Delta_i\}$ to test whether the median difference is zero without assuming normally distributed differences. Practical magnitude is summarized using a paired-sample standardized effect size:
\[
d = \frac{\bar{\Delta}}{s_{\Delta}},
\]
where $\bar{\Delta}$ is the mean of the per-model differences and $s_{\Delta}$ is their standard deviation.


    Effect magnitude levels are classified as:
    \begin{itemize}[nosep]
        \item \textbf{Negligible:} $|d| < 0.20$
        \begin{itemize}
            \item Neglibile format difference
        \end{itemize}
        \item \textbf{Small:} $0.20 \le |d| < 0.50$
        \begin{itemize}
            \item Format matters somewhat
        \end{itemize}
        \item \textbf{Medium:} $0.50 \le |d| < 0.80$
        \begin{itemize}
            \item Format choice has clear practical impact
        \end{itemize}
        \item \textbf{Large:} $|d| \ge 0.80$
        \begin{itemize}
            \item MCQ and OSQ should be treated as distinct evaluations
        \end{itemize}
    \end{itemize}

    %%% does this go here?
    \item 
        \item If the Wilcoxon test is \emph{not significant} ($p \geq 0.05$):\\
        There is no evidence that one format systematically yields higher scores across models.
        \item If the Wilcoxon test is \emph{significant} ($p < 0.05$):\\
        One format consistently gives higher scores (direction indicated by the sign of $\bar{\Delta}$).


    \item \textbf{Cross-modality consistency classification.}
    Based on the association and separation signals above, the MCQ--OSQ relationship is classified into one of the following evidence categories:
    \begin{itemize}[nosep]
        \item \textbf{Convergent evidence:} High association and negligible-to-small separation ($|d|<0.50$), with Wilcoxon not significant or directionally weak.
        \item \textbf{Partially convergent evidence:} Moderate association and/or small-to-medium separation ($0.20 \le |d| < 0.80$), indicating partial agreement with measurable format sensitivity.
        \item \textbf{Divergent evidence:} Low association and/or medium-to-large separation ($|d|\ge 0.50$), indicating that the two formats yield systematically different measurement signals on the matched subset.
    \end{itemize}
\end{enumerate}

These predefined criteria establish how cross-modality agreement will be assessed in Chapter~\ref{ch:results}. Broader implications for evidence fusion, qualification strength, or modality selection are discussed in Chapter~\ref{ch:discussion}.

\section{Objective 6: Token-Efficiency and Cost Trade-Space Analysis}
\label{sec:ch3_obj6}

Objective 6 quantifies the computational resources required to produce open-style question (OSQ) evaluation evidence and constructs a token-normalized trade space between quality and generative effort. Consistent with Research Question \ref{RQ3}, this objective treats token usage as a stable, price-agnostic proxy for computational cost. Because provider pricing and inference architectures evolve rapidly, monetary pricing is intentionally excluded. Instead, this dissertation reports token counts as the primary resource metric, enabling temporally robust comparison and reproducibility. This objective treats resource consumption as a quality--token trade space within which defensible qualification decisions must operate.


\subsection{Token Measurement and Response Policies}
\label{subsec:ch3_obj6_measurement}

Token usage was measured for each evaluation condition as the sum of prompt tokens and completion tokens:

\[
T_{\text{total}} = T_{\text{input}} + T_{\text{output}}
\]

where $T_{\text{input}}$ denotes prompt tokens and $T_{\text{output}}$ denotes generated completion tokens.

Token counts are computed using \texttt{tiktoken} with the appropriate model-specific tokenizer \cite{openai_Tiktoken_2026}. Per-item token statistics are logged via \texttt{lm-eval} JSONL outputs, enabling aggregation by model, modality, and configuration.

For OSQ evaluation, token accounting includes only model generation (prompt + completion). Judge-scoring passes are excluded from primary token metrics in order to isolate generative resource requirements from evaluation overhead. This separation ensures that reported values reflect model production cost rather than downstream scoring infrastructure.

To standardize response length and enable controlled trade-space analysis, OSQ answers were constrained using a maximum token amount of 500 tokens, which is approximately four paragraphs. No early stopping criteria were imposed. This policy ensures that token consumption reflects full response generation under a fixed upper bound. Together, these instrumentation policies define a consistent and reproducible token measurement framework. Together, these instrumentation policies define a consistent and reproducible token measurement framework. As tokenization is model-specific, token counts should be interpreted as a consistent within-model resource measure under the given tokenizer rather than a strictly universal text-length measure across all providers \cite{openai_Tiktoken_2026, huggingface_SummaryTokenizers_2026,sennrich_NeuralMachineTranslation_2016, mielke_WordsCharactersBrief_2021, kudo_SentencePieceSimpleLanguage_2018, kudo_SubwordRegularizationImproving_2018}. 

\subsection{Token-Efficiency Metrics and Trade-Space Construction}
\label{subsec:ch3_obj6_trade_space}

Using the recorded token statistics, a quality--token trade space can be constructed to evaluate generative efficiency.

For each model, the following quantities are computed:

\begin{itemize}[nosep]
    \item Mean prompt tokens per OSQ response, $\overline{T}_{\text{input}}$.
    \item Mean completion tokens per OSQ response, $\overline{T}_{\text{output}}$.
    \item Mean total tokens per OSQ response.
    \[
        \overline{T}_{\text{total}} = \overline{T}_{\text{input}} + \overline{T}_{\text{output}}
    \]

\end{itemize}

To link resource consumption to performance, a scalar efficiency metric is defined:

\[
\text{Tokens-per-score} =
\frac{\overline{T}_{\text{total}}}{\overline{S}_{\text{OSQ}}}
\]

where $\overline{S}_{\text{OSQ}}$ denotes the mean OSQ score for the model under the given configuration. Lower values indicate greater generative efficiency (fewer tokens required per unit of evaluated quality).

The quality--token trade space is constructed by plotting mean OSQ score against mean total tokens per response. A Pareto frontier is then identified. A model lies on the frontier if no alternative model achieves both:

\begin{enumerate}[nosep]
    \item Equal or higher mean OSQ score, and
    \item Equal or lower mean token consumption.
\end{enumerate}

Models strictly below and to the right of the frontier are dominated and represent less efficient trade-offs. Frontier models represent resource-efficient candidates under token-constrained evaluation regimes.

This construction does not assert that lower token usage implies higher qualification. Rather, it clarifies the computational envelope within which robustness checks, replications, and OSQ scoring can be conducted. Token counts are used here as a stable proxy for generative effort; they do not directly measure wall-clock latency, memory consumption, or hardware utilization. In addition, reasoning-oriented models may consume more completion tokens under identical caps, shifting their position in the trade space without implying inferior capability. These scope constraints ensure that quality--token comparisons are interpreted strictly within the boundaries of generation-based resource accounting.
